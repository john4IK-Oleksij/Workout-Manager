# SPEC 04 — Seed-дані та перевірка базових операцій

## 1. Мета завдання

Створити скрипт `seed.py`, який автоматично наповнює базу даних тестовими користувачами та тренуваннями.

Перевірити роботу реалізованих у SPEC 03 операцій:

- Створення користувачів.
- Створення тренувань.
- Отримання списку тренувань.
- Фільтрація за власником.
- Пагінація.

Основне джерело вимог — `ORM_MySQL(1).docx`.

Дотримуватися структури та принципів із `mission.md`.

На цьому етапі не реалізовувати статистичні запити. Мета — підготувати надійний набір даних для наступних етапів.

## 2. Файли для створення та зміни

Створити:

```text
project/
│
├── seed.py
│
└── ...
```

За потреби змінити:

- `README.md`

Використовувати наявні:
- `app/database.py`
- `app/models.py`
- `app/schemas.py`
- `app/services/users_service.py`
- `app/services/workouts_service.py`

Не дублювати ORM-моделі або логіку підключення до БД у `seed.py`.

## 3. Вимоги до тестових користувачів

Створити щонайменше трьох користувачів.

Приклад набору:

| name | email |
|---|---|
| Ivan Petrenko | ivan@example.com |
| Olena Kovalenko | olena@example.com |
| Andrii Shevchenko | andrii@example.com |

Вимоги:

1. У кожного користувача має бути унікальний email.
2. Усі записи повинні відповідати ORM-моделі `User`.
3. Користувачі повинні створюватися через SQLAlchemy ORM.
4. Дані мають бути відтворюваними між запусками скрипта.

Можна використати ці приклади або інші аналогічні тестові значення.

## 4. Вимоги до тестових тренувань

Створити щонайменше 15 тренувань.

Тренування повинні бути розподілені між усіма трьома користувачами.

Обов'язково використовувати всі чотири види:

- `run`
- `gym`
- `yoga`
- `swim`

### Вимоги до розподілу дат

Дати тренувань повинні охоплювати три календарні місяці.

Використати конкретні дати, а не випадкову генерацію.

Для кожного тренування вказати:

- `owner_id`
- `title`
- `kind`
- `duration_min`
- `distance_km`
- `done_on`

### Вимоги до різноманітності даних

Набір повинен містити:

1. Тренування різних видів.
2. Різну тривалість.
3. Різну дистанцію.
4. Тренування тривалістю менше 60 хвилин.
5. Тренування тривалістю 60 хвилин або більше.
6. Тренування із нульовою дистанцією, наприклад `gym`.
7. Кілька тренувань одного користувача.
8. Користувачів із різною кількістю тренувань.

Це потрібно, щоб наступні агрегатні запити повертали різні та показові результати.

## 5. Вимоги до скрипта seed.py

Створити самостійний скрипт:

`seed.py`

Він повинен:

1. Використовувати `SessionLocal` із `app/database.py`.
2. Використовувати ORM-моделі `User` і `Workout`.
3. Створювати тестові дані через SQLAlchemy ORM.
4. Забезпечувати правильний порядок створення записів: спочатку користувачі, потім тренування.
5. Використовувати зовнішні ключі `owner_id`.
6. Виконувати `commit()` після успішного додавання даних.
7. Виконувати `rollback()` у разі помилки.
8. Гарантовано закривати сесію.
9. Виводити зрозуміле повідомлення про результат виконання.

Не використовувати сирі SQL-запити для створення тестових записів.

### Відтворюваність

Повторний запуск `seed.py` не повинен створювати дублікати користувачів і тренувань.

Реалізувати контроль повторного наповнення.

Допустимий простий підхід:

- Перевірити, чи існують seed-користувачі.
- Якщо база вже містить відповідний seed-набір, не додавати його повторно.
- Повідомити, що тестові дані вже присутні.

Не видаляти користувачів або тренування, які не належать до seed-набору.

Не очищати всю базу даних під час запуску скрипта.

## 6. Транзакційність

Додавання користувачів і тренувань повинно бути узгодженим.

Якщо під час створення тренувань виникає помилка:

- Виконати rollback.
- Не залишати частково створений seed-набір.
- Вивести зрозуміле повідомлення про помилку.
- Не показувати конфіденційні параметри підключення.

Використовувати одну транзакцію для створення узгодженого набору даних, якщо це сумісно з поточною реалізацією.

## 7. Перевірка seed-даних

Після виконання скрипта перевірити:

- Кількість користувачів.
- Кількість тренувань.
- Кількість тренувань кожного користувача.
- Наявність усіх чотирьох видів тренувань.
- Діапазон дат.
- Наявність тренувань із тривалістю не менше 60 хвилин.
- Наявність нульової дистанції.

Переконатися, що кожне тренування має існуючого власника.

Мінімальні вимоги:

| Показник | Очікуване значення |
|---|---:|
| Користувачі | ≥ 3 |
| Тренування | ≥ 15 |
| Види тренувань | 4 |
| Період дат | 3 місяці |

## 8. Перевірка API

Використовуючи запущений FastAPI, перевірити базові операції.

### 8.1 Користувачі

Перевірити:

`POST /users`

Створити додаткового тестового користувача.

Переконатися, що:
- Відповідь має HTTP 201.
- Повертається правильний `id`.
- Email зберігається.
- Повторний email відхиляється з HTTP 409.

### 8.2 Створення тренувань

Перевірити:

`POST /workouts`

Створити тренування для існуючого користувача.

Переконатися, що:
- Відповідь має HTTP 201.
- Повертається правильний `owner_id`.
- Дата та числові значення збережені коректно.
- `distance_km=0` приймається.
- Некоректний `kind` відхиляється.
- `duration_min=0` відхиляється.

### 8.3 Отримання списку

Перевірити:

`GET /workouts`

Перевірити варіанти:

- Усі тренування.
- Тренування одного користувача.
- `limit=5`.
- `limit=5&offset=5`.
- `owner_id` разом із пагінацією.
- Відсутність тренувань для користувача.

Переконатися, що результати стабільно відсортовані за `id`.
