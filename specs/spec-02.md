# SPEC 02 — ORM-моделі та створення таблиць MySQL

## 1. Мета завдання

Створити дві ORM-моделі SQLAlchemy 2.1:

- `User`
- `Workout`

Налаштувати зв'язок між ними, визначити типи колонок, первинні та зовнішні ключі, обмеження й правила цілісності даних.

Реалізувати створення таблиць у MySQL / MariaDB 10.4.32 через SQLAlchemy ORM metadata.

Основне джерело вимог — `ORM_MySQL(1).docx`, розділ із предметною областю.

Технічний підхід має відповідати `mission.md` та вивченим матеріалам про SQLAlchemy ORM.

## 3. ORM-модель User

Створити клас `User`, який успадковується від `Base`.

Визначити такі поля:

| Поле | SQLAlchemy тип | Обмеження |
|---|---|---|
| id | Integer | Primary key, autoincrement |
| name | String(100) | NOT NULL |
| email | String(255) | UNIQUE, NOT NULL |

Вимоги:

1. `id` — первинний ключ з автоматичною генерацією значення.
2. `name` — обов'язкове поле, максимальна довжина 100 символів.
3. `email` — обов'язкове поле, максимальна довжина 255 символів.
4. `email` має бути унікальним на рівні бази даних.

Використовувати SQLAlchemy 2.x декларативний стиль із `Mapped` та `mapped_column`.

## 4. ORM-модель Workout

Створити клас `Workout`, який успадковується від `Base`.

Визначити поля:

| Поле | SQLAlchemy тип | Обмеження |
|---|---|---|
| id | Integer | Primary key, autoincrement |
| owner_id | Integer | Foreign key → users.id, NOT NULL |
| title | String(100) | Назва тренування |
| kind | String(30) | Вид тренування |
| duration_min | Integer | Більше 0 |
| distance_km | Numeric(6,2) | Може бути 0 |
| done_on | Date | Дата тренування |

### Вимоги до полів

**id**
- Первинний ключ.
- Автоматичне збільшення.

**owner_id**
- Обов'язковий зовнішній ключ на `users.id`.
- Забезпечує належність тренування конкретному користувачу.

**title**
- Рядок довжиною до 100 символів.

**kind**
- Рядок довжиною до 30 символів.
- Допустимі значення відповідно до ТЗ:
  - `run`
  - `gym`
  - `yoga`
  - `swim`

Забезпечити перевірку допустимих значень на рівні бази даних через `CheckConstraint` або еквівалентний механізм SQLAlchemy.

**duration_min**
- Ціле число.
- Значення повинно бути строго більшим за 0.
- Забезпечити обмеження на рівні бази даних через `CheckConstraint`.

**distance_km**
- Використовувати `Numeric(6, 2)`.
- Дозволити значення 0.
- Не замінювати тип `Numeric` на `Float`.
- Не додавати обмеження строгої додатності, оскільки нульова дистанція допустима для тренувань у залі.

**done_on**
- Тип `Date`.
- Зберігає дату тренування без часу.

## 5. Спільна декларативна база

Якщо в `database.py` ще не визначено декларативну базу, створити:

```python
class Base(DeclarativeBase):
    pass
```

Розмістити `Base` у відповідному модулі, щоб усі ORM-моделі використовували одну спільну базу.

Не створювати окремий `Base` для кожної моделі.

Уникати циклічних імпортів між `database.py` та `models.py`.

## 6. Зв'язок User ↔ Workout

Реалізувати ORM relationship:

- Один `User` має багато `Workout`.
- Один `Workout` належить одному `User`.

Використати:

- `relationship()`
- `back_populates`

Очікувані атрибути:

У `User`:

`workouts`

У `Workout`:

`owner`

Логіка:

```text
User
  |
  | one-to-many
  |
Workout
```

Вимоги:

1. Relationship має бути двостороннім.
2. `User.workouts` повинен повертати колекцію тренувань користувача.
3. `Workout.owner` повинен повертати відповідного користувача.
4. Зв'язок має використовувати зовнішній ключ `Workout.owner_id`.

Не додавати каскадне видалення, якщо воно не передбачене вимогами проєкту.

## 7. Створення таблиць

Реалізувати механізм створення таблиць через:

`Base.metadata.create_all()`

Використати вже створений SQLAlchemy engine із `database.py`.

Важливо:

- Перед створенням таблиць моделі мають бути імпортовані.
- Обидві моделі повинні бути зареєстровані в `Base.metadata`.
- Таблиці створюються в правильному порядку з урахуванням зовнішнього ключа.
- Повторний запуск створення таблиць не повинен спричиняти помилку, якщо вони вже існують.

Не використовувати ручне створення таблиць через SQL.

На цьому етапі не впроваджувати Alembic, оскільки це не є вимогою початкового ТЗ.

## 8. Перевірка структури БД

Після створення таблиць перевірити в MySQL:

### Таблиця users

- Існує `users`.
- Є `id`, `name`, `email`.
- `id` є PRIMARY KEY.
- `email` має UNIQUE constraint.
- `name` та `email` не допускають NULL.

### Таблиця workouts

- Існує `workouts`.
- Є всі сім обов'язкових колонок.
- `id` є PRIMARY KEY.
- `owner_id` є FOREIGN KEY на `users.id`.
- `duration_min` має CHECK constraint `duration_min > 0`.
- `kind` має обмеження допустимих значень.
- `distance_km` має точність `Numeric(6,2)`.
- `done_on` має тип DATE.

Переконатися, що обмеження реально присутні в MySQL, а не лише описані в Python-коді.

## 10. Перевірка роботи

Провести такі перевірки:

1. Запустити застосунок із налаштованим MySQL.
2. Виконати створення таблиць.
3. Переконатися, що обидві таблиці існують.
4. Перевірити типи колонок та обмеження.
5. Перевірити зв'язок між `User` і `Workout`.
6. Спробувати створити користувача.
7. Спробувати створити тренування з існуючим `owner_id`.
8. Перевірити, що тренування доступне через `User.workouts`.
9. Перевірити, що користувач доступний через `Workout.owner`.

Додатково перевірити відмову БД для:

- Повторного email.
- Від'ємної або нульової тривалості.
- Невідомого значення `kind`.
- Посилання на неіснуючого користувача через `owner_id`.

Перевірити, що нульова дистанція приймається.
