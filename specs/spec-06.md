# SPEC 06 — Агрегатні запити: By Month, Top Users та Done Ratio

## 1. Мета

Реалізувати три статистичні ендпоінти FastAPI на SQLAlchemy 2.1 та MySQL / MariaDB 10.4.32:

- `GET /stats/by-month`
- `GET /stats/top-users`
- `GET /stats/done-ratio`

Усі обчислення мають виконуватися на рівні MySQL через SQLAlchemy ORM/Core expressions. Не завантажувати всі тренування в Python для подальшої агрегації.

## 2. Передумови

Перед початком мають бути готові:

- SQLAlchemy-моделі `User` і `Workout`;
- підключення до MySQL;
- Pydantic-схеми;
- CRUD-ендпоінти;
- `app/routers/stats.py`;
- `app/services/stats_service.py`;
- ендпоінти `/stats/summary` та `/stats/by-kind`.

Дотримуватися наявної структури проєкту та стилю реалізації попередніх статистичних ендпоінтів.

## 3. GET /stats/by-month

### Призначення

Повернути статистику тренувань користувача в розрізі місяців.

### Параметри

- `owner_id: int` — обов'язковий query-параметр.

### Логіка запиту

1. Відфільтрувати тренування за `Workout.owner_id == owner_id`.
2. Отримати рік і місяць із `Workout.done_on` через MySQL-функцію `DATE_FORMAT`.
3. Згрупувати записи за цим виразом.
4. Для кожного місяця обчислити:
   - кількість тренувань;
   - сумарну дистанцію.

Використати SQLAlchemy-вираз на основі `func.date_format(Workout.done_on, "%Y-%m")`.

Зберігати вираз місяця в окремій змінній і використовувати той самий вираз у `SELECT` та `GROUP BY`.

Для сумарної дистанції обробити можливий `NULL` через `func.coalesce`.

### Очікуваний формат відповіді

```json
[
  {
    "month": "2025-01",
    "workouts_count": 4,
    "total_distance_km": 18.5
  }
]
```

Якщо записів немає, повернути порожній список.

## 4. GET /stats/top-users

### Призначення

Показати користувачів, які виконали не менше заданої кількості тренувань.

### Параметри

- `min_workouts: int` — мінімальна кількість тренувань; значення за замовчуванням `3`.

### Логіка запиту

1. Побудувати запит із таблиць `User` та `Workout`.
2. Виконати `JOIN` користувачів із їхніми тренуваннями.
3. Згрупувати результати за користувачем.
4. Обчислити кількість тренувань кожного користувача через `func.count`.
5. Застосувати `HAVING`, щоб залишити користувачів із кількістю тренувань не меншою за `min_workouts`.
6. Відсортувати результат за кількістю тренувань за спаданням.

Для підрахунку використовувати SQL-агрегацію, а не підрахунок завантажених ORM-об'єктів у Python.

### Очікуваний формат відповіді

```json
[
  {
    "user_id": 1,
    "name": "Alex",
    "workouts_count": 8
  }
]
```

Якщо жоден користувач не відповідає умові, повернути порожній список.

## 5. GET /stats/done-ratio

### Призначення

Порахувати кількість тривалих тренувань користувача та загальну кількість його тренувань.

### Параметри

- `owner_id: int` — обов'язковий query-параметр.

### Логіка запиту

1. Відфільтрувати тренування за `Workout.owner_id == owner_id`.
2. Обчислити загальну кількість тренувань.
3. Обчислити кількість тривалих тренувань, для яких `duration_min >= 60`.
4. Для умовного підрахунку використати `func.count` разом із `case`.

Приклад виразу:

```python
func.count(
    case(
        (Workout.duration_min >= 60, Workout.id)
    )
)
```

Не використовувати `FILTER`, оскільки реалізація має бути сумісною з MySQL / MariaDB 10.4.32.

### Очікуваний формат відповіді

```json
{
  "owner_id": 1,
  "long_workouts_count": 3,
  "total_workouts_count": 8
}
```

Якщо користувач існує, але тренувань немає, обидва лічильники мають дорівнювати `0`.

Якщо `owner_id` не відповідає жодному користувачу, повернути відповідь згідно з узгодженою в проєкті поведінкою для невідомого користувача — бажано HTTP 404.

## 6. Pydantic-схеми

Створити окремі схеми відповідей для кожного ендпоінта:

- `MonthlyStatsResponse`;
- `TopUserStatsResponse`;
- `DoneRatioResponse`.

Назви можна адаптувати до вже прийнятого в проєкті стилю, але схеми мають залишатися окремими та зрозумілими.

Вимоги:

- коректні типи полів;
- `Decimal` для десяткової дистанції, якщо це відповідає схемам попередніх статистичних ендпоінтів;
- жодного повернення сирих SQLAlchemy-об'єктів замість DTO;
- усі три ендпоінти повинні мати явно вказаний `response_model`.

## 8. Тестування

Перевірити такі сценарії:

### By Month

- користувач має тренування в декількох місяцях;
- місяці повертаються окремими групами;
- дистанція правильно підсумовується;
- тренування іншого користувача не потрапляють у результат;
- користувач без тренувань отримує порожній список.

### Top Users

- користувач із кількістю тренувань рівно `min_workouts` потрапляє в результат;
- користувач із меншою кількістю не потрапляє;
- результат відсортований за спаданням кількості тренувань;
- порожній результат обробляється коректно.

### Done Ratio

- тривалі тренування рахуються за умовою `duration_min >= 60`;
- тренування тривалістю рівно 60 хвилин враховується;
- коротші тренування не враховуються в `long_workouts_count`;
- загальна кількість відповідає всім тренуванням користувача;
- порожній набір тренувань повертає нульові лічильники.

## 9. Вимоги до SQL та MySQL

- Використовувати SQLAlchemy 2.x стиль запитів.
- Не виконувати агрегації в Python.
- У кожному користувацькому статистичному запиті обов'язково застосовувати фільтр за `owner_id`.
- Для групування використовувати вирази SQLAlchemy.
- Перевірити запити саме на MySQL / MariaDB 10.4.32.
- Не покладатися на SQLite для перевірки специфічної поведінки `DATE_FORMAT`.
- Не повертати SQL-текст або параметри запитів у повідомленнях про помилки.

## 10. Критерії завершення

SPEC вважається виконаним, якщо:

- усі три маршрути доступні через FastAPI;
- усі три маршрути мають Pydantic response-схеми;
- агрегації виконуються на стороні MySQL;
- `DATE_FORMAT` працює коректно;
- умовний підрахунок реалізовано через `COUNT(CASE ...)`;
- `HAVING` використовується для фільтрації агрегованої кількості користувачів;
- усі тести проходять;
- наявні маршрути `/stats/summary` та `/stats/by-kind` продовжують працювати.
