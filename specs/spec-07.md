# SPEC 07 — Безпечна динамічна агрегація `/stats/group`

## 1. Мета

Реалізувати універсальний статистичний ендпоінт:

`GET /stats/group`

Ендпоінт повинен дозволяти клієнту вибирати:

- поле, за яким групувати тренування;
- метрику, яку потрібно обчислити.

Вибір має відбуватися виключно через заздалегідь визначений whitelist SQLAlchemy-виразів.

Основний акцент цього етапу — безпека динамічних запитів і контроль допустимих параметрів.

## 2. Передумови

Перед початком мають бути реалізовані:

- моделі `User` та `Workout`;
- підключення до MySQL;
- Pydantic-схеми;
- CRUD-ендпоінти;
- статистичні маршрути з попередніх SPEC.

Використовувати наявну структуру проєкту та стиль попередніх реалізацій.

## 3. Контракт ендпоінта

### Маршрут

`GET /stats/group`

### Query-параметри

- `group_by: str` — поле групування;
- `metric: str` — метрика;
- `owner_id: int` — обов'язковий ідентифікатор власника тренувань.

Приклад запиту:

`GET /stats/group?group_by=kind&metric=sum_duration&owner_id=1`

## 4. Дозволені значення

Створити whitelist допустимих полів групування та метрик.

### GROUP_COLUMNS

Початковий набір полів групування:

- `kind` — тип тренування;
- `owner_id` — ідентифікатор користувача.

Кожному ключу має відповідати готовий SQLAlchemy-вираз, наприклад:

- `kind` → `Workout.kind`;
- `owner_id` → `Workout.owner_id`.

### METRICS

Початковий набір метрик:

- `count` — кількість тренувань;
- `sum_duration` — сумарна тривалість;
- `sum_distance` — сумарна дистанція;
- `avg_duration` — середня тривалість.

Кожному ключу має відповідати готовий SQLAlchemy-агрегат, наприклад:

- `count` → `func.count(Workout.id)`;
- `sum_duration` → `func.coalesce(func.sum(Workout.duration_min), 0)`;
- `sum_distance` → `func.coalesce(func.sum(Workout.distance_km), 0)`;
- `avg_duration` → `func.avg(Workout.duration_min)`.

Зберігати ці відповідності в окремих словниках або іншій централізованій структурі.

## 5. Критично важливі вимоги безпеки

Заборонено будувати SQLAlchemy-вирази безпосередньо з рядків, отриманих від користувача.

Не використовувати:

```python
getattr(Workout, group_by)
getattr(func, metric)
```

Не вставляти параметри користувача безпосередньо в SQL-рядки.

Правильний алгоритм:

1. Отримати `group_by` і `metric`.
2. Перевірити, чи існують такі ключі у `GROUP_COLUMNS` та `METRICS`.
3. Взяти відповідні готові SQLAlchemy-вирази зі словників.
4. Побудувати запит із перевірених виразів.
5. Виконати запит із обов'язковим фільтром `Workout.owner_id == owner_id`.

Якщо значення не входить до whitelist, повернути HTTP 422.

## 6. Валідація параметрів

Для параметрів `group_by` та `metric` використовувати `Enum` або `Literal` у Pydantic/FastAPI.

Дозволити лише значення, які відповідають whitelist.

Приклади некоректних значень:

- `group_by=unknown_field`;
- `metric=delete`;
- `metric=some_sql_expression`.

Для некоректних параметрів FastAPI має повертати HTTP 422 із зрозумілим повідомленням про помилку валідації.

Валідація через Enum або Literal не замінює whitelist у сервісі: обидва рівні мають бути узгоджені.

## 7. Логіка SQL-запиту

Після перевірки параметрів побудувати запит за такою логікою:

1. Вибрати вираз групування.
2. Вибрати агрегатну метрику.
3. Додати фільтр за `Workout.owner_id == owner_id`.
4. Виконати `GROUP BY` за вибраним виразом.
5. Отримати результати через SQLAlchemy 2.x API.

Усі агрегати мають виконуватися в MySQL, а не в Python.

Якщо метрика повертає можливий `NULL`, обробити це відповідно до її семантики та типу відповіді. Для сум використовувати `coalesce`, для середнього значення враховувати можливість відсутності даних.

## 8. Формат відповіді

Створити окрему Pydantic-схему відповіді для динамічної агрегації.

Відповідь має містити:

- значення поля групування;
- назву метрики;
- обчислене значення.

Приклад:

```json
[
  {
    "group_value": "run",
    "metric": "sum_duration",
    "value": 180
  },
  {
    "group_value": "gym",
    "metric": "sum_duration",
    "value": 240
  }
]
```

Фактичний тип `value` має відповідати вибраній метриці. Для дистанції враховувати `Decimal` і коректну JSON-серіалізацію.

Якщо груп немає, повернути порожній список.

Якщо відповідні файли вже містять потрібні структури, розширити їх, не створюючи дублікати.

## 10. Тестування

Перевірити такі сценарії:

### Коректні параметри

- `group_by=kind&metric=count`;
- `group_by=kind&metric=sum_duration`;
- `group_by=kind&metric=sum_distance`;
- `group_by=kind&metric=avg_duration`;
- `group_by=owner_id&metric=count`.

### Некоректні параметри

- невідоме поле групування;
- невідома метрика;
- спроба передати SQL-вираз замість дозволеного ключа;
- порожні значення параметрів.

У некоректних випадках має повертатися HTTP 422.

### Ізоляція даних

- результат містить тільки тренування заданого `owner_id`;
- тренування інших користувачів не впливають на агрегати;
- порожній набір даних повертає порожній список.

### Перевірка SQL

- запит виконується на MySQL / MariaDB 10.4.32;
- групування та агрегація виконуються на стороні БД;
- жоден користувацький рядок не використовується як довільний SQLAlchemy-вираз.

## 11. Критерії завершення

SPEC вважається виконаним, якщо:

- маршрут `/stats/group` працює;
- доступні тільки дозволені поля та метрики;
- whitelist зберігається централізовано;
- `getattr` для динамічного формування SQL не використовується;
- невідомі значення повертають HTTP 422;
- кожен запит обмежений `owner_id`;
- Pydantic-схема відповіді налаштована;
- усі тести проходять;
- попередні статистичні маршрути продовжують працювати.
