## 3. Бонусний ендпоінт: Running Total

### Маршрут

`GET /stats/running-total?owner_id=1`

### Призначення

Повернути список тренувань користувача з накопичувальною сумою дистанції за датами.

Для кожного запису показати:
- дату тренування;
- дистанцію конкретного тренування;
- накопичувальну дистанцію від початку вибірки до поточної дати.

### Логіка запиту

1. Відфільтрувати тренування за `Workout.owner_id == owner_id`.
2. Впорядкувати записи за `Workout.done_on`.
3. Використати `func.sum(Workout.distance_km).over(...)` для накопичувальної суми.
4. Визначити `order_by` у віконному виразі.
5. За потреби додати стабільний додатковий порядок за `Workout.id`, щоб результати з однаковою датою були передбачуваними.

Приклад основного виразу:

```python
func.sum(Workout.distance_km).over(
    order_by=Workout.done_on
)
```

Для детермінованого порядку можна використати:

```python
func.sum(Workout.distance_km).over(
    order_by=(Workout.done_on, Workout.id)
)
```

Використовувати SQLAlchemy window API через `.over()`. Не обчислювати накопичувальну суму циклом у Python.

### Очікуваний формат відповіді

```json
[
  {
    "done_on": "2025-01-10",
    "distance_km": 5.00,
    "running_total_km": 5.00
  },
  {
    "done_on": "2025-01-12",
    "distance_km": 3.50,
    "running_total_km": 8.50
  },
  {
    "done_on": "2025-01-15",
    "distance_km": 7.00,
    "running_total_km": 15.50
  }
]
```

Якщо тренувань немає, повернути порожній список.

## 4. Бонусний ендпоінт: Rank

### Маршрут

`GET /stats/rank?owner_id=1`

### Призначення

Побудувати рейтинг типів тренувань користувача за сумарною тривалістю.

### Логіка запиту

1. Відфільтрувати тренування за `Workout.owner_id == owner_id`.
2. Згрупувати записи за `Workout.kind`.
3. Обчислити сумарну тривалість кожного типу через `func.sum`.
4. Використати `func.rank().over(...)` для ранжування груп за сумарною тривалістю за спаданням.
5. Повернути тип тренування, сумарну тривалість та його ранг.

Приклад віконного виразу:

```python
func.rank().over(
    order_by=func.sum(Workout.duration_min).desc()
)
```

Агрегацію та ранжування потрібно реалізувати в SQL-запиті. Не виконувати ранжування в Python.

### Очікуваний формат відповіді

```json
[
  {
    "kind": "gym",
    "total_duration_min": 420,
    "rank": 1
  },
  {
    "kind": "run",
    "total_duration_min": 300,
    "rank": 2
  },
  {
    "kind": "yoga",
    "total_duration_min": 180,
    "rank": 3
  }
]
```

Якщо декілька типів мають однакову сумарну тривалість, `RANK()` повинен присвоїти їм однаковий ранг.

## 5. Pydantic-схеми

Додати окремі схеми відповідей:

- `RunningTotalResponse`;
- `WorkoutKindRankResponse`.

Вимоги:
- дата має серіалізуватися у форматі ISO;
- дистанція має підтримувати `Decimal`;
- накопичувальна дистанція має коректно серіалізуватися;
- тривалість має бути числовим значенням;
- ранг має бути цілим числом.

Для обох ендпоінтів явно вказати `response_model`.

## 7. Перевірка MySQL / MariaDB 10.4.32

Усі агрегатні та window-запити перевірити саме на MySQL / MariaDB 10.4.32.

Особливу увагу приділити:
- `DATE_FORMAT`;
- `GROUP BY`;
- `HAVING`;
- `CASE`;
- `COALESCE`;
- `SUM() OVER`;
- `RANK() OVER`.

Перевірити сумісність із режимом `ONLY_FULL_GROUP_BY`.

У запитах із групуванням усі вибрані неагреговані поля мають бути присутні в `GROUP BY`.

Не замінювати MySQL на SQLite для перевірки специфічних функцій MySQL або window-запитів.
