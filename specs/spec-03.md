# SPEC 03 — Pydantic-схеми та CRUD-ендпоінти

## 1. Мета завдання

Реалізувати базові API-операції для користувачів і тренувань відповідно до оригінального ТЗ `ORM_MySQL(1).docx`.

Після виконання цього етапу застосунок повинен підтримувати:

- Створення користувачів.
- Створення тренувань.
- Отримання списку тренувань.
- Фільтрацію тренувань за власником.
- Пагінацію через `limit` та `offset`.

Використовувати:
- FastAPI.
- Pydantic 2.
- SQLAlchemy 2.1 ORM.
- Уже створені моделі `User` і `Workout`.
- Підключення до MySQL із попередніх SPEC.

## 3. Pydantic-схеми користувачів

Створити окремі схеми для створення та відповіді.

### UserCreate

Поля:

| Поле | Тип | Вимоги |
|---|---|---|
| name | str | Обов'язкове, максимум 100 символів |
| email | EmailStr | Обов'язкове, максимум 255 символів |

Вимоги:

- Використовувати Pydantic 2.
- Невідомі поля заборонені через `extra="forbid"`.
- Перевіряти формат email.
- Не приймати `id` від клієнта.

### UserResponse

Поля:

| Поле | Тип |
|---|---|
| id | int |
| name | str |
| email | str |

Використати конфігурацію:

`ConfigDict(from_attributes=True)`

Схема повинна підтримувати створення відповіді безпосередньо з ORM-об'єкта.

## 4. Pydantic-схеми тренувань

Створити окремі схеми для створення та відповіді.

### WorkoutCreate

Поля:

| Поле | Тип | Вимоги |
|---|---|---|
| owner_id | int | Обов'язкове, більше 0 |
| title | str | Обов'язкове, максимум 100 символів |
| kind | str | run, gym, yoga або swim |
| duration_min | int | Більше 0 |
| distance_km | Decimal | Не менше 0, точність до 2 знаків |
| done_on | date | Обов'язкова дата |

Вимоги:

1. Перевіряти допустимі значення `kind`.
2. Перевіряти додатність `duration_min`.
3. Дозволяти `distance_km = 0`.
4. Не використовувати `float` замість `Decimal`.
5. Заборонити невідомі поля через `extra="forbid"`.
6. Не приймати `id` від клієнта.

Для `kind` бажано використати спільний `Enum`, який надалі можна буде використовувати в інших частинах застосунку.

### WorkoutResponse

Поля:

| Поле | Тип |
|---|---|
| id | int |
| owner_id | int |
| title | str |
| kind | str |
| duration_min | int |
| distance_km | Decimal |
| done_on | date |

Використати:

`ConfigDict(from_attributes=True)`

## 5. Сервіс користувачів

Реалізувати `app/services/users_service.py`.

Створити функцію:

`create_user(session, user_data)`

Логіка:

1. Отримати перевірені дані з Pydantic-схеми.
2. Створити ORM-об'єкт `User`.
3. Додати об'єкт до сесії.
4. Виконати `commit()`.
5. Виконати `refresh()`.
6. Повернути створений ORM-об'єкт.

Обробити ситуацію, коли email уже існує.

У разі порушення UNIQUE constraint:
- Виконати rollback.
- Не показувати користувачу текст SQL або внутрішні деталі БД.
- Повернути зрозумілу HTTP-помилку 409 Conflict.

Не допускати витоку деталей винятку.

## 6. Роутер користувачів

Реалізувати `app/routers/users.py`.

Endpoint:

`POST /users`

Вимоги:

- Приймає `UserCreate`.
- Викликає функцію сервісу.
- Повертає `UserResponse`.
- Повертає HTTP 201 Created.
- Не містить SQLAlchemy-запитів безпосередньо в роутері.

Приклад запиту:

```http
POST /users
Content-Type: application/json
```

```json
{
  "name": "Ivan",
  "email": "ivan@example.com"
}
```

Очікувана структура відповіді:

```json
{
  "id": 1,
  "name": "Ivan",
  "email": "ivan@example.com"
}
```

Фактичний `id` визначається базою даних.

## 7. Сервіс тренувань

Реалізувати `app/services/workouts_service.py`.

Створити дві функції.

### 7.1 create_workout(session, workout_data)

Логіка:

1. Перевірити існування користувача з переданим `owner_id`.
2. Якщо користувача немає, повернути HTTP 404.
3. Створити ORM-об'єкт `Workout`.
4. Додати об'єкт до сесії.
5. Виконати `commit()`.
6. Виконати `refresh()`.
7. Повернути створений об'єкт.

У разі помилки під час запису виконувати rollback.

### 7.2 get_workouts(session, owner_id, limit, offset)

Реалізувати отримання списку тренувань.

Використовувати SQLAlchemy 2.x:

- `select(Workout)`
- `where()`
- `order_by()`
- `limit()`
- `offset()`
- `session.scalars()`

Якщо `owner_id` переданий, фільтрувати тренування за цим користувачем.

Якщо `owner_id` не переданий, повертати всі тренування.

Для стабільного порядку результатів використовувати сортування за `Workout.id` у порядку зростання.

Пагінацію виконувати на рівні бази даних, а не після отримання всіх записів у Python.

## 8. Роутер тренувань

Реалізувати `app/routers/workouts.py`.

### 8.1 Створення тренування

Endpoint:

`POST /workouts`

Вимоги:

- Приймає `WorkoutCreate`.
- Викликає `create_workout()`.
- Повертає `WorkoutResponse`.
- Повертає HTTP 201 Created.
- Не виконує SQLAlchemy-запити безпосередньо в роутері.

Приклад:

```http
POST /workouts
Content-Type: application/json
```

```json
{
  "owner_id": 1,
  "title": "Morning run",
  "kind": "run",
  "duration_min": 45,
  "distance_km": 6.50,
  "done_on": "2026-03-15"
}
```

### 8.2 Отримання списку тренувань

Endpoint:

`GET /workouts`

Query-параметри:

| Параметр | Тип | Значення за замовчуванням |
|---|---|---|
| owner_id | int, optional | None |
| limit | int | 20 |
| offset | int | 0 |

Валідація:

- `owner_id`, якщо переданий, має бути більшим за 0.
- `limit` має бути більшим за 0.
- Максимальний `limit` — 100.
- `offset` не може бути від'ємним.

Використати FastAPI `Query` або `Annotated`.

Приклад:

```http
GET /workouts?owner_id=1&limit=10&offset=0
```

Відповідь — масив об'єктів `WorkoutResponse`.

Якщо тренувань немає, повертати порожній масив `[]` з HTTP 200.

Не повертати помилку лише через відсутність тренувань.

## 10. Обробка помилок

Забезпечити зрозумілу поведінку для типових ситуацій:

| Ситуація | HTTP статус |
|---|---|
| Користувач успішно створений | 201 |
| Тренування успішно створене | 201 |
| Email уже існує | 409 |
| Власник тренування не існує | 404 |
| Некоректні поля запиту | 422 |
| Некоректні query-параметри | 422 |
| Список тренувань отримано | 200 |

Не повертати:
- SQL-запити.
- Паролі БД.
- Connection strings.
- Внутрішні traceback.
- Чутливі деталі винятків.

## 12. Перевірка

Перевірити через Swagger UI або HTTP-клієнт.

Виконати такі сценарії:

1. Створити користувача.
2. Створити другого користувача.
3. Спробувати створити користувача з повторним email.
4. Створити тренування для першого користувача.
5. Створити тренування для другого користувача.
6. Спробувати створити тренування для неіснуючого користувача.
7. Отримати всі тренування.
8. Отримати тренування конкретного користувача.
9. Перевірити `limit`.
10. Перевірити `offset`.
11. Передати `limit=101` і перевірити HTTP 422.
12. Передати від'ємний `offset` і перевірити HTTP 422.
13. Передати невідоме поле в JSON і перевірити HTTP 422.
14. Перевірити створення тренування з `distance_km=0`.
15. Перевірити, що некоректний `kind` відхиляється.
